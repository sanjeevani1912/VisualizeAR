## Milestone B1: plans, comments, decisions, audit (PLAN.md phase 2)
Routes (all under `/api`): `GET /plans`, `POST /plans`, `POST /plans/:id/versions`, `POST /plans/:id/withdraw`,
`POST /plans/:id/start-review`, `POST /plans/:id/decision`, `POST /plans/:id/comments`, `GET /audit`, `GET /audit/verify`
(admin and auditor only).
1. **Layout checking first** (`server/src/layout.ts`): same accepted shape, same rejection messages
   (`Invalid layout file: <path> - <message>`), 500-object cap, default sizes for missing dimensions (`ASSET_DEFAULTS`: 11 asset types),
   generated ids and names, rotation normalised to 0-360, the content hash.
   - **The content hash risk:** the Node hash is computed over `JSON.stringify` of the normalised layout. Python's `json.dumps`
     differs (floats like `10.0`, exponents, key order, spacing, unicode). Write a function that reproduces JavaScript number and string
     serialisation exactly, and prove it with test vectors **generated by running the Node code** on several layouts, including
     `server/scripts/fixtures/app-layout-v2.json` (the app's own export), floats like `1e-7`, large numbers and unicode names.
2. **Routes and rules** (from `PLAN.md` "Behaviours that are easy to get subtly wrong"):
   - a plan the user may not see is **404**, never 403;
   - reject and changes-requested need a reason of at least 10 characters; approve does not;
   - a decision must name the **latest** version, otherwise 409, and is recorded against that version;
   - plan codes are `TP-YYYY-NNNN`, numbered per year (watch for two requests at once: use a transaction or a DB sequence so codes never repeat);
   - resubmitting keeps the old plan name when the new layout still has the default name `Untitled plan`;
   - `start-review` answers `{ok:true, changed:false}` when it does not apply, not an error;
   - planners see only their own plans; reviewers, admins, auditors see all; use `api/rules.py`;
   - `GET /plans` returns each plan with `versions` (with parsed `layout`), `decisions`, `comments`, `attachments` (with `url`
     `/api/attachments/<id>`) in the exact shape of `loadPlans()` in `server/src/plans.ts`;
   - `GET /audit` filters entries to plans the caller may see (see `listAudit` in `audit.ts`).

## Milestone B4: PostgreSQL
Follow `DhruvAR\docs\prompts\demo-and-deployment\REAL-DATA-AND-POSTGRES.md`, tasks D1 and D2's PostgreSQL notes:
1. Add `psycopg[binary]`; make `config/settings.py` choose the database from environment variables (SQLite stays the default).
   **The current SQLite-only `OPTIONS` (`transaction_mode`, `timeout`) must not be passed to PostgreSQL.**
2. A `docker-compose` file with `postgres:16` and a named volume; password from a git-ignored env file.
3. Run `migrate` and the **whole test suite on PostgreSQL**.
4. **Audit log concurrency:** `audit()` chains each entry to the previous hash. On SQLite, `BEGIN IMMEDIATE` serialised writers; on
   PostgreSQL two simultaneous writes could chain to the same previous entry. Take a row lock on the latest audit row
   (`select_for_update`) or a PostgreSQL advisory lock inside the transaction, and add a test that fires concurrent writes from
   several threads and then checks `verify_chain()`.
5. Plan-code numbering and the login lock-out must also be safe under concurrency; test them.
6. A short operations note: how to start, stop, back up and restore PostgreSQL. Document and **stop**.
